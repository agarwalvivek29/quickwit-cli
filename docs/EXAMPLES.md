# Examples — a first run of `qw`

This is a real, captured walkthrough of the `qw` CLI searching Quickwit logs
**through `qwproxy`** (the auth + audit proxy). Every command below is
authenticated with an OIDC token and recorded in the audit trail.

Everything here is reproducible against the local simulation stack:

```sh
make sim-up     # keycloak + seeded quickwit + postgres + qwproxy
make demo       # runs exactly the walkthrough below
make sim-audit  # shows the audit rows the walkthrough produced
make sim-down
```

> The transcript was generated by `deploy/compose/demo/demo.sh`. The binary is
> built without a version stamp there, so it reports `qw/dev`.

## 1. Log in and pick a context

A context points `qw` at a proxy endpoint and an OIDC issuer. You log in once;
the token is cached (0600) in `~/.config/qw/config.yaml` and refreshed
automatically.

```sh
qw context use stage
qw login                 # opens your browser (Okta/Keycloak); --device for headless
```

```console
$ qw context list
CURRENT  NAME   ENDPOINT             ISSUER                                LOGGED-IN
*        stage  http://qwproxy:9000  http://keycloak:8080/realms/quickwit  yes

$ qw whoami
context:  stage
endpoint: http://qwproxy:9000
  identity: dev@example.com
  token expires: 2026-08-06T03:33:01Z

$ qw ping
http://qwproxy:9000 is reachable
quickwit version: v0.8.2
```

## 3. Search

A bare search defaults to the last 15 minutes; widen it with `--since`,
`--from`, `--to`. Output is a table by default.

```console
$ qw search core-logs level:ERROR --since 2h
6 hits (showing 6) in 4ms
TIMESTAMP             LEVEL  SERVICE   MESSAGE
2026-08-06T02:24:35Z  ERROR  checkout  request 25 handled by checkout
2026-08-06T02:26:15Z  ERROR  payments  request 20 handled by payments
2026-08-06T02:27:55Z  ERROR  checkout  request 15 handled by checkout
2026-08-06T02:29:35Z  ERROR  payments  request 10 handled by payments
2026-08-06T02:31:15Z  ERROR  checkout  request 5 handled by checkout
2026-08-06T02:32:55Z  ERROR  payments  request 0 handled by payments
```

`-o json` gives you the raw documents (pipe to `jq`); `-o raw` prints just the
message. Level values are colorized in a terminal (`--no-color` to disable).

```console
$ qw search core-logs level:ERROR --since 2h -o json
6 hits (showing 6) in 1ms
[
  {
    "level": "ERROR",
    "message": "request 25 handled by checkout",
    "service": "checkout",
    "timestamp": "2026-08-06T02:24:35Z"
  },
  ...
]
```

Project specific columns with `--fields` (dot paths supported for nested docs):

```console
$ qw search core-logs service:payments --fields timestamp,level,service,message --since 2h
15 hits (showing 15) in 1ms
TIMESTAMP             LEVEL  SERVICE   MESSAGE
2026-08-06T02:23:35Z  INFO   payments  request 28 handled by payments
2026-08-06T02:24:15Z  WARN   payments  request 26 handled by payments
...
2026-08-06T02:32:55Z  ERROR  payments  request 0 handled by payments
```

## 4. Count and volume-over-time

```console
$ qw count core-logs '*' --since 2h
30

$ qw histogram core-logs '*' --since 2h --interval 5m
2026-08-06T02:20:00Z  6   ################
2026-08-06T02:25:00Z  15  ########################################
2026-08-06T02:30:00Z  9   ########################
```

## 5. Follow (tail)

`qw tail` polls on an interval and prints new lines as they arrive
(chronological, deduped). Ctrl-C to stop.

```console
$ qw tail core-logs '*'
request 29 handled by checkout
request 28 handled by payments
request 27 handled by checkout
request 26 handled by payments
...
```

## 6. The proxy is a read-only, authenticated gate

The same endpoints, hit directly, show what `qwproxy` enforces:

```console
$ curl -s -o /dev/null -w '%{http_code}\n' http://qwproxy:9000/api/v1/version
401                     # no bearer token -> rejected

$ curl -s -o /dev/null -w '%{http_code}\n' -XPOST \
    http://qwproxy:9000/api/v1/core-logs/ingest -H "authorization: Bearer $TOKEN" --data '{}'
403                     # authenticated, but writes are blocked by the read-only allowlist
```

## 7. What the audit trail recorded

Every request above (except the rejected `401`/`403`, which never reach the
audit stage) landed in Postgres — attributed to the **CLI** (`user_agent`,
`cli_version`) and the **user** (`principal_email` from the OIDC token), with
the **search query itself** captured (`query_body`) but **never the response
body**.

```console
$ make sim-audit
 principal_email | user_agent | cli_version | method | index     | status | latency_ms | query_body
-----------------+------------+-------------+--------+-----------+--------+------------+---------------------------------------------------------------
 dev@example.com | qw/dev     | dev         | GET    | core-logs |    200 |          0 |                                    (qw ping / indexes / fields)
 dev@example.com | qw/dev     | dev         | POST   | core-logs |    200 |          5 | {"query":"level:ERROR","max_hits":20,"start_timestamp":...}
 dev@example.com | qw/dev     | dev         | POST   | core-logs |    200 |          1 | {"query":"service:payments","max_hits":20,"start_timestamp":...}
 dev@example.com | qw/dev     | dev         | POST   | core-logs |    200 |          1 | {"query":"*","max_hits":0,"start_timestamp":...}          (count)
 dev@example.com | qw/dev     | dev         | POST   | core-logs |    200 |          1 | {"aggs":{"histogram":{"date_histogram":{"field":"timestamp","fixed_interval":"5m"}}},"query":"*",...}
 ...
```

Summary of the run:

```console
 total_rows | agents | agent  | ver
------------+--------+--------+-----
         12 |      1 | qw/dev | dev

 method | count | with_query
--------+-------+------------
 GET    |     6 |          0     # version / list / describe / fields — no body
 POST   |     6 |          6     # every search + histogram, query captured
```

That is the whole point of the project: Quickwit OSS keeps no record of who
searched what — `qwproxy` does, without ever storing the (potentially huge)
response payloads.
